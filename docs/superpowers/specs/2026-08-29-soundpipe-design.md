## 1. 背景与目标

用户需要把电脑内正在播放的声音转发为"麦克风输入"，供微信/QQ/钉钉语音通话、腾讯会议、OBS 直播/推流/录屏、以及只认麦克风输入的特定软件使用。

核心诉求：

- **按应用程序勾选**要转发的声音（不是全系统一锅端），也可整系统转发
- 目标"麦克风"可选任意录音设备（用户已安装 VB-Cable 与 Voicemeeter）
- 本地监听可开关；真实麦克风可参与混音
- 桌面应用，资源占用小；低延迟优先
- 功能面板式 UI、全局快捷键、预设方案、电平指示条

**安全声明**：所有音频数据仅在内存中处理，不写入磁盘（日志除外，且不含音频内容）、不发送到网络。

## 3. 技术选型

- **C# / .NET 8 / WPF**：原生 Windows 桌面应用，音频与 COM 交互开发效率高，占用可控
- **NAudio**：设备枚举、WasapiCapture、WasapiOut、重采样（MediaFoundationResampler）
- **进程循环捕获**：`IAudioClient` + `ActivateAudioInterfaceAsync`（`AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` + 目标 PID 参数），系统级 API，无需 DLL 注入；与 OBS"应用音频捕获"同款技术。需自写 COM interop（P/Invoke），社区有成熟参考实现。UWP 应用（如部分商店版应用）大多可用 PROCESS_LOOPBACK 捕获；个别受保护 DRM 流（如部分受版权保护的内容）系统会拒绝，届时提示该应用无法捕获
- **整系统捕获**：`WasapiLoopbackCapture`
- **全局热键**：`RegisterHotKey` Win32 API
- **应用会话枚举**：`IAudioSessionManager2` 会话枚举器获取正在发声的进程（PID、显示名、图标）
- **配置**：JSON 持久化于 `%APPDATA%\SoundPipe\`

被否决的备选：整系统循环捕获（不满足按应用选择）；C++ 捕获核心（占用收益仅几十 MB，工程复杂度翻倍）。其他已评审否决项见附录 B。

## 4. 总体架构

```
┌─ 音频源（可多选，运行时可增删）─────────┐
│ ① 应用进程捕获（按勾选，每应用一路流）   │
│ ② 整系统循环捕获（模式二选一）          │
│ ③ 真实麦克风捕获（可选，设备可选）       │
└──────────────┬───────────────┘
               ▼
        混音器（48k/2ch/float32，按源音量，软限幅，RMS 电平）
               ▼
┌─ 输出 ───────────────────────────────┐
│ 目标设备（默认 CABLE Input 等虚拟输入端）│
│ 监听设备（开关控制，独立缓冲吸收时钟漂移）│
└──────────────────────────────────────┘
```

### 4.1 模块划分

- **SoundPipe.Core**（类库，可单元测试）
  - `Capture/AppProcessCapture`：进程循环捕获（含 COM interop）
  - `Capture/SystemLoopbackCapture`：整系统捕获
  - `Capture/MicCapture`：真实麦克风捕获
  - `Mixer`：多源重采样→按源增益→叠加→软限幅→主输出缓冲；每源 RMS 电平事件；**线程安全的 `AddSource`/`RemoveSource`（锁内换引用，运行中增删源不停流）**
  - `Output/DualOutput`：写目标设备；监听开启时写监听设备（独立缓冲 + 独立重采样，见 §5.6）
  - `SessionMonitor`：定时枚举当前发声应用（含名称、图标、活动状态）
  - `DeviceService`：设备枚举、默认设备识别、虚拟输入端友好命名、**热插拔事件（自实现 `IMMNotificationClient`：`OnDeviceStateChanged` / `OnDeviceAdded` / `OnDeviceRemoved` / `OnDefaultDeviceChanged` / `OnPropertyValueChanged`）→ 事件驱动刷新流与 UI**
  - `PresetManager`：预设与上次状态的序列化
  - `HotkeyService`：RegisterHotKey 封装（含防抖）
  - `Logging`：滚动文件日志
- **SoundPipe.App**（WPF）
  - 主窗口（功能面板式单屏布局）+ 托盘（NotifyIcon）
  - `AppViewModel`：状态与命令绑定

### 4.2 线程模型

| 线程 | 模型 | 职责 |
|---|---|---|
| UI 主线程 | STA | WPF 界面、托盘、ViewModel；**不做任何音频工作** |
| 音频引擎线程（每流一个） | MTA | WASAPI 事件回调处理：捕获读、输出写；缓冲区预分配 |
| 混音线程 | MTA | 汇聚各源环形缓冲 → 混音 → 写输出环形缓冲 |
| SessionMonitor 定时器 | 后台 | 每 1s 轮询会话，差异比对后经 Dispatcher 推送 UI |

COM 初始化：各音频线程自行 `CoInitializeEx(COINIT_MULTITHREADED)`；UI 线程保持 STA。跨线程数据仅经**每源一个的 SPSC lock-free 环形缓冲**（自实现定长 float 环形缓冲，预分配、无锁无分配）与不可变快照传递；UI 更新统一经 Dispatcher。

### 4.3 控制流 / 事件流

```
热键 / 托盘菜单 / 面板按钮 ──→ 引擎 Start/Stop（幂等，切换中拒绝重复触发）
设备热插拔事件 ──→ DeviceService ──→ 受影响的流重建 + UI 下拉刷新 + 气泡提示
SessionMonitor(1s) ──→ 应用列表差异刷新（活动状态驱动 F12 闪烁指示）
捕获流异常 ──→ 自动重启策略（§5.6）
```

### 4.4 事件驱动 vs 轮询

- WASAPI 全部采用**事件驱动回调模式**（`AUDCLNT_STREAMFLAGS_EVENTCALLBACK`），不用睡眠轮询，保证低延迟与低 CPU
- 仅 SessionMonitor 用 1s 轮询（系统无"应用开始发声"推送事件）

## 5. 关键设计决策

### 5.1 数据流与格式协商

1. 各捕获源以自身格式产出 float32 帧
2. Mixer 统一重采样到 48kHz/2ch（源格式不符时用 MediaFoundationResampler）
3. 按源音量相乘后叠加；叠加结果过软限幅（tanh 型，阈值 -1dBFS）防削波（**tanh 零延迟，适合实时；不采用需 look-ahead 的峰值限幅**）
4. 主输出缓冲按目标设备 WASAPI 流写入；监听流独立缓冲（采样率不匹配时独立重采样）
5. 电平：每源计算 RMS，UI 以 30fps 节流刷新

**格式协商规则（捕获端与输出端一致适用）**：

```
请求 48k/2ch/float32 → IsFormatSupported？
  ├─ 是 → 直接使用
  ├─ 就近格式支持（如 44.1k）→ 使用最近格式 + 重采样到引擎格式
  └─ 否 → 退回设备 MixFormat + MediaFoundationResampler 重采样
```

### 5.2 按应用捕获（F1）

- 通过 `ActivateAudioInterfaceAsync` 以 `PROCESS_LOOPBACK` 模式打开指定 PID（含子进程开关）的捕获流
- 请求格式 48kHz/2ch/float32；协商失败按 §5.1 回退
- 应用退出 → 对应流停止并从勾选列表移除；无源时输出静音，引擎保持运行（保证通话软件不断流）
- 用户勾选/取消勾选时经 `Mixer.AddSource/RemoveSource` 动态增删，**引擎不停流**

### 5.3 目标设备语义（F3）

- 目标设备下拉列出**所有播放（渲染）设备**；对名称含 `CABLE Input`、`Voicemeeter Input`、`Voicemeeter VAIO`、`Line 1 (Virtual Audio Cable)` 等的设备标注"虚拟输入端"图标并排序靠前，首个命中的作为默认
- 选中普通扬声器时给出提示："普通扬声器上的转发不会被通话软件识别为麦克风"
- 首次运行若全列表无虚拟输入端 → F13 引导流程（说明 + VB-Cable 官方下载链接 + 安装后热插拔事件自动刷新）
- 说明：真实硬件麦克风设备无法被用户态程序注入（系统限制）；混合人声通过 F5 在工具内混音后送入虚拟输入端实现

### 5.4 预设与状态（F8）

- 预设字段：名称、模式（按应用/整系统）、勾选应用（按**进程名**存储，如 `chrome.exe`，加载时与当前会话匹配；不存 PID）、目标/监听/麦克风设备（按 MMDevice ID，失效时按名称回退匹配）、各音量、延迟 ms、快捷键
- 存储：`%APPDATA%\SoundPipe\presets.json`；`%APPDATA%\SoundPipe\state.json` 记录上次使用预设
- 启动加载上次预设但不自动开始转发（手动点"开始转发"或快捷键）

### 5.5 UI 布局（功能面板式）

```
┌ SoundPipe ────────────────────────────┐
│ 模式：(●)按应用  ( )整系统             │
│ ┌ 发声应用列表（图标/名称/活动指示●/   │
│ │  电平条/勾选，音量%旁显）            │ │
│ └────────────────────────────────┘  │
│ 目标设备: [CABLE Input ▼]             │
│ 监听: [✓] 设备: [扬声器 ▼]            │
│ 麦克风: [🎤 默认麦克风 ▼] 音量 80%     │
│ 延迟: ──○── 20ms     [■ 停止转发]     │
│ 预设: [微信通话 ▼] [保存]  总电平 ▮▮▮  │
│ 状态栏: 运行中 · 按应用 · 2 个应用      │
└──────────────────────────────────────┘
```

- 托盘：图标颜色区分运行/停止；左键单击切换窗口显隐；右键菜单=开始/停止、监听开关、预设切换、退出；关闭窗口=最小化到托盘
- 快捷键设置：设置面板内"录制按键"弹窗（KeyDown 捕获修饰键+键值），注册前检测系统占用冲突，冲突则提示更换
- 电平条：-60dB~0dB 对数刻度，绿→黄→红三级配色
- 基本无障碍：控件补 `AutomationProperties.Name`

### 5.6 双输出、时钟漂移与流异常恢复

- 目标/监听两条输出流**各自独立环形缓冲与独立重采样器**，混音结果写入两条缓冲；两设备时钟漂移由缓冲深度（约 2×周期）吸收，缓冲将满/将空时以采样复制/丢弃微调对齐，**复制与丢弃处用 2–4 样本 crossfade 淡入淡出过渡，避免硬切换引入 click/pop**；不做全局时钟同步
- **流异常自动重启**：捕获/输出流出错即重建流，首次重试延迟 1s；连续失败 3 次 → 停止该源/输出并在 UI 状态栏与气泡中提示原因；目标输出流失败则引擎整体停止（转发已不可用）

### 5.7 发布与签名

- 发布配置：**框架依赖单文件**（`PublishSingleFile=true`，产物 ≤ 5MB，需 .NET 8 Desktop Runtime，启动时检测并给出下载引导）为默认；另提供**自包含单文件**（约 120MB）给无运行时环境。WPF 不支持 `PublishTrimmed`（不兼容裁剪），故放弃 40MB 自包含目标
- **SmartScreen/签名**：未签名二进制首启会被 SmartScreen 拦截（个人使用点"仍要运行"即可）；分发阶段再评估购买 OV 代码签名证书，不在首版范围内

### 5.8 延迟定义与测量（N2）

- 定义：端到端延迟 = 源应用写入音频帧 → 目标设备实际发声的时间
- 构成：捕获周期 + 混音缓冲 + 输出周期 + 设备内部延迟；工具内以 performance counter 打点统计"捕获帧到达→输出流写入"段，设置面板显示实测值
- 端到端验证（脉冲打点法）：测试模式向两路同时注入 10ms 脉冲——一路经工具→CABLE Output→录音，一路直接走扬声器→同一录音设备，比对两脉冲时间差

## 6. 错误处理与边界

| 场景 | 行为 |
|---|---|
| Windows < 10 2004 | 按应用捕获不可用 → 启动时提示并自动切整系统模式，UI 禁用"按应用" |
| 无音频会话（静音） | 应用列表空显示引导文案；引擎空转输出静音 |
| 目标设备拔出 | 自动重建到当前默认设备，气泡提示"已切换到 XXX，可能不再是虚拟输入端"，需用户确认是否改选 |
| 监听设备拔出 | 自动重建到当前默认设备并简单提示 |
| 勾选应用退出 | 移除勾选、销毁其捕获流 |
| 目标为独占模式占用 | WASAPI 打开失败 → 提示"设备被占用"，不降级（共享模式在此场景物理不可行） |
| 重复启动 | Mutex 单实例；二次启动通过命名 EventWaitHandle 通知首实例，首实例经 FindWindow + SetForegroundWindow 唤起已有窗口 |
| 快捷键注册失败-启动时 | 冲突弹窗提示更换快捷键，不阻塞主功能 |
| 快捷键注册失败-运行时被抢占 | 气泡提示"快捷键已失效"，转发功能不受影响，设置面板可重新注册 |
| 流异常 | 按 §5.6 自动重启策略（1s 重试 ×3，超限停源并提示） |
| 受保护内容（DRM） | 进程循环捕获被系统拒绝 → 该应用标记"无法捕获" |

- 单元测试：混音叠加/增益/软限幅数学、格式协商回退选择、预设序列化往返、预设按进程名匹配逻辑、热键防抖、AddSource/RemoveSource 并发、**DualOutput 双流独立重采样正确性**、**流异常重启计数器（1s 重试 ×3 超限停源）**
- 兼容性测试矩阵：

| 维度 | 覆盖 |
|---|---|
| OS | Win10 2004 / Win10 22H2 / Win11 23H2+ |
| 虚拟声卡 | VB-Cable 最新版；Voicemeeter Banana；二者共存 |
| 声卡 | Realtek 集成 / USB 外置 / 蓝牙耳机（含热插拔） |

- 手动验证矩阵：
  1. 微信语音通话：对方可听到勾选应用的声音；监听开关生效
  2. OBS：添加"音频输入捕获"选 CABLE Output，电平随系统声音跳动
  3. 腾讯会议：会议中音频设置选虚拟设备，播放本地音乐对方可闻
  4. 热插拔：转发中拔掉耳机 → 自动落到默认设备且不崩

## 附录 B：已评审否决项（存档备查）

| 项 | 否决理由 |
|---|---|
| UWP 捕获方案 | PROCESS_LOOPBACK 对多数 UWP 可用；仅 DRM 流例外，按 §6 处理 |
| 设备 ID 哈希化 | MMDevice ID 非敏感信息；哈希致预设跨设备不可恢复 |
| 硬编码并发流上限 8 | 无依据；以性能监控动态判断 |
| MediaFoundation 精简版回退 | 标准 Win10/11 均含 MF；回退机制降为低优 |
| 峰值限幅替代 tanh | tanh 零延迟；峰值限幅需 look-ahead 增加延迟 |
| 共享模式回退（独占场景） | 设备被独占时共享模式物理不可行，逻辑矛盾 |
| 卸载残留驱动 | SoundPipe 不装驱动；仅需清理 `%APPDATA%\SoundPipe\` |
| ClickOnce 部署 | .NET 8 不推荐，不支持 self-contained |
