# SoundPipe 设计文档 —— 两轮查漏补缺总结

经过首轮查漏补缺和对该报告的二次审阅，共识别出以下需要补充或修正的内容，按优先级归类如下。

---

## 高优先级（开发前必须明确）

| 项 | 问题 | 来源 |
|---|---|---|
| COM 线程模型 | 文档未说明 STA/MTA 选择，直接影响 WASAPI 回调可靠性。建议 UI 主线程 STA，音频引擎独立 MTA 线程 | 首轮 #4.1 → 审阅确认 |
| 设备格式协商 | 目标设备和捕获端均未说明格式协商失败时的回退策略。需补充 `IsFormatSupported` 使用逻辑和自动重采样 | 首轮 #1 + #5.1 → 审阅补充"捕获端同样重要" |
| GC 暂停风险 | .NET GC 偶发毫秒级暂停，对 20ms 实时缓冲可能造成卡顿。需设置 `GCLatencyMode.SustainedLowLatency` 或非托管内存管理 | 审阅新增 |
| 安全声明 | 应显式声明"所有音频数据仅在内存中处理，不写入磁盘、不发送到网络" | 审阅新增 |
| 数字签名 | 无签名会被 SmartScreen 拦截，影响分发 | 审阅新增 |

## 中优先级（M3/M4 前完成）

| 项 | 问题 | 来源 |
|---|---|---|
| 日志系统 | 缺少滚动日志文件，问题排查困难。建议 `%APPDATA%\SoundPipe\logs\`，5 文件轮转各 1MB | 首轮 #2.5 → 审阅确认 |
| 多设备时钟漂移 | 双输出流时钟不一致会导致缓冲溢出/欠载，需独立缓冲 + 采样率转换器吸收漂移 | 首轮 #4.5 → 审阅确认 |
| 流异常自动重启 | 捕获/输出流中断后缺乏恢复策略。建议 1 秒后重试，连续 3 次失败则停止该源 | 首轮 #4.7 → 审阅确认 |
| 首次运行引导 | 系统无虚拟音频设备时缺少引导流程。需提示安装 VB-Cable 并提供下载链接 | 首轮 #2 修正 + 审阅确认 |
| 多麦克风选择 | "真实麦克风"应下拉选择具体输入设备，而非固定默认 | 首轮 #6 → 审阅确认 |
| 设备热插拔刷新 | `DeviceService` 检测变化后应事件驱动自动刷新 UI 下拉列表 | 首轮 #3.4 → 审阅修正为事件驱动 |
| 应用发声状态指示 | 列表中应显示音频活动状态（如闪烁指示器），即使未勾选也能判断 | 首轮 #3.1 → 审阅确认 |
| 快捷键设置 UI | 文档说"可自定义"但缺少交互设计，需增加按键捕获弹窗和冲突检测 | 首轮 #3.3 → 审阅确认 |
| 音量数值显示 | 滑条旁应显示百分比或 dB 值 | 首轮 #3.5 → 审阅确认 |
| 延迟测量方法 | N2 给出 20ms 指标但未定义如何测量，需补充端到端测量方案 | 首轮 #6.1 → 审阅确认 |
| 兼容性测试矩阵 | 需覆盖 Win10/11 不同版本 + VB-Cable/Voicemeeter 不同版本 + 主流声卡 | 首轮 #6.3 → 审阅确认 |
| .NET 发布参数 | 需明确 `PublishSingleFile` + `TrimMode` 配置以满足 ≤40MB 要求 | 首轮 #7.3 → 审阅确认 |
| 动态添加/移除源 | 混音器需支持 `AddSource`/`RemoveSource` 线程安全操作，避免用户勾选时停流 | 首轮 #8.1 → 审阅确认 |

## 已否决的建议（首轮报告中提出但审阅认为不成立）

| 项 | 否决理由 |
|---|---|
| UWP 捕获方案（高优）→ 降为中优 | Win10 2004+ 的 PROCESS_LOOPBACK 对大多数 UWP 实际可用；Spotify 桌面版已非 UWP |
| 设备 ID 哈希化 | MMDevice ID 不含敏感信息，哈希化反而导致预设跨设备不可恢复 |
| 硬编码并发流上限 8 个 | 缺乏依据，48kHz/float32 数据量极小，应通过性能监控动态判断 |
| MediaFoundation 精简版回退 | 标准 Win10/11 均包含 MF，不在兼容范围内；回退机制保留但降低优先级 |
| 峰值限幅替代 tanh | tanh 零延迟，适合实时场景；峰值限幅需 look-ahead 会增加延迟 |
| 共享模式回退（独占场景） | 文档已说明不降级独占；设备被独占时共享模式物理不可行，逻辑矛盾 |
| 卸载残留驱动 | SoundPipe 不安装驱动，VB-Cable 为用户自行安装，仅需清理 `%APPDATA%\SoundPipe\` |
| ClickOnce 部署 | .NET 8 已不推荐 ClickOnce，不支持 self-contained 发布 |

## 需在架构图中补充的要素

- **控制流/事件流**：热键→引擎启停、设备热插拔→流重建、SessionMonitor→UI 刷新的交互关系
- **线程模型**：UI 线程（STA）、音频捕获线程（MTA）、混音线程、输出线程的职责划分
- **事件驱动 vs 轮询**：WASAPI 缓冲回调模式选择

---

整体评估：原始设计文档覆盖了核心功能和主要边界，架构方向正确。主要短板集中在**实时音频工程细节**（线程模型、GC、时钟漂移、格式协商）和**用户体验补全**（引导、反馈、状态指示）。以上高优项建议在 M2 前纳入设计文档，中优项在 M3/M4 前明确，低优项可在首个版本发布后迭代。
